## Doppler video generation in ChatGPT

The existing Doppler simulation already supports agent-directed WebM recording in the browser through these WebMCP tools:

- `create_doppler_video`
- `get_doppler_video_status`
- `stop_doppler_video`
- `download_doppler_video`

This capability must be preserved and exposed through the ChatGPT MCP App UI rather than reimplemented as a server-side renderer.

### Why video remains browser-side

The current Doppler recorder uses browser-native runtime features:

- `AudioContext`
- `MediaStreamDestination`
- `MediaRecorder`
- canvas/visual recording
- live synthesized or sampled vehicle audio
- local browser download

Browser audio activation requires an explicit user gesture. Therefore a remote MCP server cannot silently create the same audiovisual file on behalf of the user without changing the architecture and introducing a server-side rendering pipeline.

### Target ChatGPT video flow

```text
User
  ↓
"Show me the Doppler effect as a short video"
  ↓
ChatGPT chooses Doppler video capability
  ↓
Esbiko MCP App opens Doppler Video Studio
  ↓
User clicks Generate / Start once
  ↓
Browser activates audio + recording
  ↓
Esbiko runs deterministic director timeline
  ↓
WebM finalizes
  ↓
Download button becomes available
  ↓
User saves the video locally
```

### Supported video stories

The existing director currently supports:

- `single_pass` — one source crosses the observer halfway through the video
- `two_vehicle` — two sequential vehicle/source passes

Configurable values include:

- duration: 10–60 seconds
- source speed: 10–60 m/s
- emitted frequency: 100–1000 Hz
- first/second sound source
- vehicle/siren/Esbiko voice samples
- fixed 9:16 output for short-form video

The director already verifies that an audio track exists and rejects silent recordings.

### ChatGPT-facing UX

When the user asks for a short video, ChatGPT should not merely return a link or claim that a file was created. The MCP App should present:

1. selected scenario and scientific parameters
2. generated before/after frequency comparison
3. a clear **Generate video** button
4. live progress and current story phase
5. audio-track / signal verification
6. a **Download WebM** button only after status becomes `ready`

A first-click requirement is expected and intentional because the browser must unlock audio recording through a user gesture.

### Reuse requirement

Do not duplicate the director logic. Reuse:

- `src/simulations/subjects/physics/acoustics/Doppler/director/dopplerDirector.js`
- `src/simulations/subjects/physics/acoustics/Doppler/hooks/useDopplerDirector.js`
- existing recorder integration in `Dopplersimulator.jsx`
- existing Doppler WebMCP video tools

The MCP App should become a presentation/control surface over this existing capability.

### Example user request

```text
Show the Doppler effect as a 20-second video with an ambulance approaching and then moving away. I want to hear the pitch change and download the video.
```

Expected behavior:

```text
ChatGPT
  → selects Esbiko Doppler video mode
  → opens embedded Doppler Video Studio
  → user starts recording
  → Esbiko creates audiovisual WebM
  → UI reports ready
  → user downloads locally
```

This video workflow is part of the Doppler MCP App v0.2 milestone.


## MCP App UI v0.2

The first ChatGPT-renderable Esbiko UI is registered as:

```text
ui://esbiko/doppler-v1.html
```

The `run_doppler_experiment` tool links to this resource through the standard MCP Apps metadata:

```text
_meta.ui.resourceUri
```

and also publishes the ChatGPT compatibility alias:

```text
_meta["openai/outputTemplate"]
```

The resource MIME type is:

```text
text/html;profile=mcp-app
```

The component supports inline and fullscreen display modes.

### Embedded simulation

The component embeds the existing Esbiko Doppler runtime:

```text
https://www.esbiko.com/experiments/physics.acoustics.doppler/run
```

This preserves the existing production simulation rather than copying its React implementation into a second ChatGPT-specific application.

The MCP App resource declares a narrow CSP and allows frames only from:

```text
https://www.esbiko.com
```

No third-party frame origin is allowed.

### Result synchronization

The parent MCP App listens for the standard MCP Apps lifecycle message:

```text
ui/notifications/tool-result
```

and renders the authoritative structured result returned by `run_doppler_experiment`:

- emitted frequency
- observed frequency
- frequency shift
- motion
- scientific interpretation

The embedded simulation remains independently interactive.

### Design rule

The Doppler scientific tool must remain fully useful when a client does not render MCP App UI. The UI is an enhancement, not a dependency of the scientific result.

### v0.2 acceptance criteria

The phase is considered complete when:

1. the public MCP server exposes `ui://esbiko/doppler-v1.html`
2. `run_doppler_experiment` advertises that UI resource
3. the resource can be read by an official MCP client
4. the scientific tool still returns the expected 533.29 Hz reference result
5. ChatGPT renders the MCP App when the connected Esbiko plugin calls the tool
6. the embedded Esbiko simulation loads in the component
7. interactive video generation remains available from the browser-based Doppler runtime
