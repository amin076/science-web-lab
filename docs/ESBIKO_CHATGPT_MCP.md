# Esbiko for ChatGPT — MCP Integration\n\n## Status\n\n- Phase: MCP proof of concept\n- Version: 0.1.0\n- First simulation: physics.acoustics.doppler\n- Primary goal: prove the first real ChatGPT → MCP → Esbiko → scientific-result cycle\n- Custom ChatGPT UI: intentionally deferred until the tool-only cycle is verified\n\n## Purpose\n\nEsbiko already has a scalable simulation registry, a common runtime, a Platform API, and browser-side WebMCP tooling. The ChatGPT integration must reuse those layers instead of creating a second simulation platform.\n\nThe first integration therefore exposes a small server-side MCP surface that can return a deterministic scientific Doppler result. Once that connection is verified in ChatGPT, the same adapter pattern can be generalized to additional simulations and later connected to an MCP App UI.\n\n## Existing architecture that remains authoritative\n\nThe existing simulation architecture is unchanged:\n\n1. simulation implementation under src/simulations/\n2. permanent simulation ID\n3. central simulationRegistry\n4. experiment metadata\n5. common RunSimulation runtime\n\nThe existing WebMCP implementation remains in place:\n\n- src/webmcp/WebMcpSiteTools.jsx\n- src/webmcp/registerWebMcpTools.js\n- src/webmcp/siteTools.js\n- Doppler WebMCP adapter/tools under src/simulations/subjects/physics/acoustics/Doppler/\n\nThe MCP server is an additional integration layer, not a replacement.\n\n## OpenAI architecture reference\n\nCurrent OpenAI plugin documentation describes MCP servers as the mechanism for exposing live tools to ChatGPT and Codex. Tool-first integration is recommended before optional UI is added. A production endpoint should be reachable over HTTPS and normally use Streamable HTTP at a stable /mcp URL.\n\nOfficial references reviewed for this phase:\n\n- https://developers.openai.com/plugins\n- https://developers.openai.com/plugins/quickstart\n- https://developers.openai.com/plugins/build/mcp-server\n- https://developers.openai.com/plugins/build/app-quickstart\n\n## Version 0.1 architecture\n\nUser\n  ↓\nChatGPT\n  ↓\nEsbiko MCP endpoint\n  ↓\nMCP tool dispatch\n  ↓\nEsbiko Doppler scientific service\n  ↓\nstructured scientific result\n  ↓\nChatGPT physics explanation\n\nThe endpoint is hosted by the existing Firebase Functions backend and routed through Firebase Hosting at:\n\nhttps://www.esbiko.com/mcp\n\nThe first version is intentionally stateless. It does not preserve a browser simulation session.\n\n## MCP tools in v0.1\n\n### list_science_simulations\n\nPurpose:\n\n- prove MCP tool discovery\n- identify simulations currently exposed through the ChatGPT MCP integration\n- return the permanent Esbiko simulation ID and existing capability metadata\n\nFor v0.1 this list contains only physics.acoustics.doppler.\n\n### run_doppler_experiment\n\nPurpose:\n\n- run Esbiko's scientific Doppler model\n- accept structured experiment parameters\n- return a model-readable scientific result\n\nInputs:\n\n- motion: approaching, receding, or stationary\n- emittedFrequencyHz\n- sourceSpeedMps\n- sourcePositionM\n- observerPositionM\n- observerVelocityMps\n\nStructured outputs include:\n\n- permanent simulation ID\n- speed of sound\n- source and observer parameters\n- signed source velocity\n- emitted frequency\n- observed frequency\n- frequency ratio\n- frequency shift percentage\n- physical motion interpretation\n\n## Scientific consistency\n\nThe server-side calculation intentionally follows the same coordinate convention and equations used by the browser simulation in:\n\nsrc/simulations/subjects/physics/acoustics/Doppler/utils/dopplerPhysics.js\n\nThe v0.1 server-side service lives at:\n\nfunctions/mcp/dopplerService.js\n\nThis gives ChatGPT a deterministic scientific result even when no browser UI is open.\n\nReference experiment:\n\n- emitted frequency: 440 Hz\n- source speed: 60 m/s\n- source position: 250 m\n- observer position: 500 m\n- observer velocity: 0 m/s\n- motion: approaching\n\nExpected Esbiko result:\n\n- observed frequency: 533.29 Hz\n- frequency shift: +21.20%\n- status: Approaching / Higher pitch\n\n## HTTP endpoint\n\nFirebase Hosting routes /mcp and /mcp/** to the mcp Cloud Function.\n\nThe proof-of-concept endpoint implements the minimal stateless MCP/JSON-RPC surface required for the first cycle:\n\n- initialize\n- notifications/initialized\n- ping\n- tools/list\n- tools/call\n\nNo authentication is required in v0.1 because the exposed operations are public, read-only scientific calculations and public simulation discovery.\n\n## Why v0.1 is intentionally small\n\nThe proof of concept must first answer one question:\n\nCan ChatGPT discover an Esbiko tool, call it through an MCP endpoint, receive a scientific result generated by Esbiko, and use that result in the conversation?\n\nUntil that passes, do not add:\n\n- user accounts or OAuth\n- persistent simulation sessions\n- video generation\n- browser remote control\n- multiple simulation conversions\n- custom MCP App UI\n- public plugin-submission packaging\n\n## Verification\n\nRun these commands from the repository root:\n\nnpm run test:mcp-doppler\nnpm run test:platform-api\nnpm run test:webmcp\nnpm run build\n\nThen deploy Firebase Hosting and Functions and verify the public endpoint.\n\nFor the first ChatGPT test, connect the custom MCP server using:\n\nhttps://www.esbiko.com/mcp\n\nSuggested first prompt:\n\nUse Esbiko to show the Doppler effect for a 440 Hz source moving toward a stationary observer at 60 m/s. Tell me the observed frequency and explain why it changes.\n\nExpected tool sequence:\n\nChatGPT → list_science_simulations (optional) → run_doppler_experiment → structured Esbiko result → physics explanation\n\n## Next phase after the first successful cycle\n\nAfter the first real ChatGPT cycle passes:\n\n1. move the transport implementation onto the official MCP SDK before public distribution\n2. add contract tests with MCP Inspector\n3. add a browser/session bridge for stateful simulation control\n4. connect the existing Doppler WebMCP actions to the server-side MCP model where appropriate\n5. add an MCP App UI so the simulation can appear interactively inside ChatGPT\n6. define a reusable simulation-agent adapter contract\n7. migrate one additional simulation, preferably Simple Pendulum\n8. only then scale to more simulations\n\n## Generalization target\n\nLong term, each simulation should expose only the capabilities it actually supports through a small reusable adapter contract, for example: discover, read-state, configure, run, pause, reset, and measure.\n\n## Non-goals\n\nThis work does not change permanent simulation IDs, existing routes, classroom behavior, Firestore documents, or the common simulation runtime. Backward compatibility with the existing Esbiko website remains mandatory.\n
